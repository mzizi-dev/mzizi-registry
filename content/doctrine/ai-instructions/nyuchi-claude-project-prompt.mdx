You are working on Mzizi — the open design system and DNA-double-helix frontend architecture, governed by the Bundu Foundation and operated by nyuchi, that powers the bundu ecosystem (mukoko, nyuchi, shamwari, bundu, nhimbe).

═══════════════════════════════════════════════
NO HARDCODED NUMBERS
═══════════════════════════════════════════════

This prompt deliberately contains no counts. Component counts, node counts, and token counts drift as the system evolves. When you need a current number, query the database:

- get_node_counts()           — per-node component counts
- get_system_counts()          — system-wide totals
- get_token_counts()           — token counts per category (every styling-* collection)
- get_node_categories(N)      — category breakdown for node N
- get_architecture()           — every node and rung with its strand, backbone, covenant, rules, and live counts
- get_node_documents(...)      — raw documents for any node or collection
- get_node_detail(N)           — single-node detail (covenant, stakeholder, rules, categories)
- get_latest_release()         — current version
- get_accessibility_summary()  — WCAG and color-blindness validation summary

═══════════════════════════════════════════════
THE DNA DOUBLE HELIX
═══════════════════════════════════════════════

Two entwined backbones, held together by cross-cutting rungs. Node numbers are
labels, not a sequence, and the set is never capped — read get_architecture()
for the live model rather than assuming a range.

ENGINEERING BACKBONE — strands, and the nodes that sit on them:
  core-guarantee   N2 Primitives · N4 Safety · N5 Resilience · N8 Assurance
                   "The guarantees travel unchanged, always."
  shipped          N3 Brand · N6 Pages · N7 Shell
                   "In the box, but free to evolve."
  swappable        N1 Tokens
                   "Fork along the seams, not everywhere."
  spine            the harness — "what makes the parts one body."

MEANING BACKBONE:
  genetic-code     Ubuntu doctrine + bundu conventions —
                   "the sequence everything is read from."
  transcription    "Doctrine is data, not tribal knowledge."

RUNGS — cross-cutting, bridging both backbones, bound to no single strand:
  N9  Fundi          "Failure is a learning event." (self-healing)
  N10 Documentation  "The system documents itself."
  N11 Discovery      "If the machine can't see it, it doesn't exist." (SEO/AIO)

A node consumes from the strand below it on the same backbone — never
sideways and never upward. Rungs bridge both backbones and are never
imported by a node.

Each node has exactly ONE sub-label value in the components.node_label column:
tokens / primitive / brand / safety / resilience / pages / shell / assurance / fundi / documentation / discovery. Read the live set with SELECT DISTINCT node_label FROM components rather than assuming this list is complete.

═══════════════════════════════════════════════
SOURCE CODE LIVES IN THE DATABASE
═══════════════════════════════════════════════

components.source_code is the canonical store. The frontend repo pulls from the DB at build time.
When you add or modify a component, write the TypeScript directly to components.source_code via SQL.
status=alpha means registered without source; status=stable means production source in DB.

═══════════════════════════════════════════════
IMPLEMENTATION RULES
═══════════════════════════════════════════════

1. CSS values live only in N1 tokens. Other nodes reference via var().
2. Icons come from @/lib/icons (nyuchi-icons registry). Never import lucide-react directly.
3. N2 primitives never import useNyuchiHarness. They use cn() for classNames and carry data-slot.
4. N3 brand components always destructure { log, motion, LiveRegion } from useNyuchiHarness.
5. N3 brand components always use the nyuchi- prefix in their name.
6. N6 pages are pure composition — no inline buttons, cards, SVGs, or brand fonts.
7. Every component has data-slot and data-portal attributes.
8. All status colors use semantic tokens (--status-success, --status-error, etc).
9. Third-party brand colors (Ethereum, Google, EcoCash) are the only raw hex exceptions.
10. Buttons, inputs, avatars, badges, toggles are ALWAYS pill-shaped (borderRadius: 9999).
11. Touch targets default to 48px (styling-touch-targets.comfortable). 44px absolute minimum.
12. Density-aware components reference styling-density values, never hardcode tier behaviour.
13. RTL support: use logical CSS properties (margin-inline-start, padding-inline-end), not physical. rtl-conformity-check N8 validates this at runtime.
14. Versioning: 4.0.x = internal patches. 4.1.0 = first public release.
15. Fundi creates GitHub issues for failures — humans stay in the loop.

═══════════════════════════════════════════════
DESIGN TOKENS — STYLING-* COLLECTIONS
═══════════════════════════════════════════════

N1 tokens are persisted in first-class styling-* collections with canonical CSS variable names:

Visual: styling-minerals, styling-semantic-colors (incl. hc_light_value/hc_dark_value),
        styling-spacing, styling-typography (incl. letter_spacing/fluid clamps/font_features),
        styling-radius, styling-shadow, styling-motion, styling-breakpoints, styling-z-index.

Sizing & accessibility: styling-icon-sizes, styling-touch-targets, styling-component-specs.

Density: styling-density (compact/comfortable/spacious tiers), styling-density-breakpoints.

Validation: styling-accessibility-checks (WCAG contrast + color-blindness flags per pair, light + dark).

Reference: styling-categories, styling-ecosystem, styling-meta.

Query tokens directly rather than assuming values. The DB is the source of truth.

═══════════════════════════════════════════════

- calculate_contrast_ratio(fg, bg) — WCAG 2.1 contrast ratio between two hex colors
- get_accessibility_summary()      — passing AA/AAA counts plus color-blindness validation status

═══════════════════════════════════════════════
KEY FUNCTIONS
═══════════════════════════════════════════════

- log_version(name, type, comment, author) — track component changes
- log_release_v2(...) — log a release; call mcp_describe('release') for the live signature
- get_component_links(name) — get all URLs for a component
- create_fundi_issue(component, severity, error_type, source) — create healing issue

═══════════════════════════════════════════════
RENAMES ARE SAFE
═══════════════════════════════════════════════

Foreign keys on component_docs and component_demos use ON UPDATE CASCADE.
Renaming a component in the components table automatically updates its docs and demos rows.
component_versions has no FK — update it manually when renaming.
Also check registry_dependencies arrays on other components for stale references.

═══════════════════════════════════════════════
ACCESSIBILITY HEALING LOOP
═══════════════════════════════════════════════

An N8 component `accessibility-audit` runs daily via pg_cron and files Fundi issues for any color-blindness regressions. To validate manually: SELECT run_accessibility_audit(). To get current status: SELECT * FROM get_accessibility_summary(). To simulate a single color: simulate_color_blindness(hex, cb_type).

═══════════════════════════════════════════════
SKILLS — AI AGENT DOCTRINE DISTRIBUTION
═══════════════════════════════════════════════

The `skills` table stores multi-agent AI skills (Claude Code, Cursor, Copilot, Cline, Windsurf). Skills are the doctrine every AI agent working in a Nyuchi-ecosystem project should read.

Surfaces:
  - GET /api/v1/skills           — catalogue (no body)
  - GET /api/v1/skills/{name}    — full skill with body_mdx (Accept: text/markdown for CLI)
  - list_skills() SQL function   — same catalogue from the DB
  - get_skill(name) SQL function — single skill with body
  - MCP tool: list_skills
  - MCP tool: get_skill

Distribution:
  - npx @nyuchi/design-cli init         — bootstraps a new app with skills pre-installed
  - npx @nyuchi/design-agent-skills     — installs skills into ./.claude/skills/ in an existing project
  - npx skills add nyuchi/agent-skills — via the community skills CLI
  - /plugin install nyuchi@nyuchi-design-system — Claude Code plugin marketplace

The three published skills:
  - nyuchi-design-system  — core doctrine (the DNA double helix, minerals, DB-first)
  - scaffold-component    — how to create a new component correctly
  - ecosystem-app-setup   — bootstrap a new ecosystem app end-to-end
