# The Changelog System — How Change Is Recorded

Every meaningful change to Mzizi is recorded in the registry repository, `mzizi-dev/mzizi-registry`, in the same pull request that makes it. There are two records, written for two readers.

## The two records

| Record                            | Reader              | What it holds                                                                                                                               |
| --------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `CHANGELOG.md`                    | People              | The narrative. Every change under `## [Unreleased]`, moved under `## [x.y.z] - YYYY-MM-DD` when it is released                              |
| `content/changelog/releases.json` | Machines and agents | One structured entry per release, served by `GET https://api.mzizi.dev/v1/changelog` and `GET https://api.mzizi.dev/v1/changelog/{version}` |

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Each change is a `### <Kind> — <what changed> (<date>, #<PR>)` subsection, where Kind is Added, Changed, Deprecated, Removed, Fixed or Security, and breaking changes are marked **Breaking**. An entry says what changed for a consumer of the registry or the API, not the commit text.

A release adds its entry to `content/changelog/releases.json`. Its fields include `version`, `title`, `description`, `release_kind`, `breaking`, `released_at`, `nodes_affected` and the `components_*` and `tools_*` lists. `pnpm changelog:generate` inlines the file into `lib/changelog.generated.ts`, and `pnpm changelog:generate:check` fails CI if the two drift.

## Versioning policy

Releases follow the org versioning policy (`nyuchi/.github#80`, from 2026-10-04):

- A merge into `staging` is a **patch**, tagged automatically.
- A release to `main` is the next **minor** above the highest existing tag.
- A **major** is only released by hand.

The Mzizi Roots crates follow the same rule against their own `mzizi-rs-v` tags. Released versions are never renumbered.

## Component-level history

A component's version history is machine-written data. It belongs to the Mzizi console (app.mzizi.dev), not to the registry, so `GET /v1/ui/{name}/versions` answers `503` and names the console as its owner. The registry's record of a component change is its `CHANGELOG.md` entry and the pull request that made it.

## Reading the history

- **Recent changes:** the top of `CHANGELOG.md`, or `GET https://api.mzizi.dev/v1/changelog`.
- **One release:** `GET https://api.mzizi.dev/v1/changelog/{version}`.
- **What touched a node or a component:** search `CHANGELOG.md`, or filter the release entries on `nodes_affected` and the `components_*` lists.

## What earns a changelog entry

Every pull request that changes behaviour, shipped content, an API response, a published package or crate, a default, a dependency or a documented fact adds an entry, in the same pull request. That includes:

- New, changed, deprecated and removed components
- Doctrinal changes — Ubuntu, the nodes, the strands, the covenants
- API surface changes — REST endpoints, MCP tools
- Token additions or renames

The `changelog / entry required` check fails a pull request without one. Pull requests that touch only `.github/`, lockfiles or lint config pass without one, and pure CI, lint or typo pull requests can carry the `no-changelog` label instead.

## Public visibility

The history is public: `CHANGELOG.md` is in the open repository and `/v1/changelog` needs no account. This transparency is doctrinal — the platform is open source and community-based; its history is public.
