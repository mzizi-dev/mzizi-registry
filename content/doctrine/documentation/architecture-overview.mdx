# Architecture Overview — Two Architectures, One Ecosystem

The Bundu Foundation operates two distinct architectures, governed by different rules, joined at clearly defined seams. Conflating them is a category error.

## The two architectures

| Architecture | Governs | Canonical model | Where it lives |
| -- | -- | -- | -- |
| **Application architecture** | How UI / app components are built, composed, and shipped | **Mzizi DNA Helix** | `component_documents/{primitives,brand,pages,shell,styling-*,accessibility,resilience,observability,fundi,...}` |
| **Data architecture** | How data is stored, owned, moved, and contributed | **Substrate model + four-category ownership** | `documentation-architecture-{cloud,data,data-ownership,pipeline,sovereignty,removed}` and `genetic-code-conventions/substrate-decision` |

These are not layers of one stack. They are two architectures, intersecting at one defined point (see "the seam" below).

## Application architecture — the Mzizi DNA Helix

The application architecture describes how user-facing software is structured. Mzizi is the framework (the DNA), authored by Nyuchi, used inside Nyuchi and Mukoko products, available to any adopter.

| Strand component | Role | Owner |
| -- | -- | -- |
| Core guarantee | `primitives` · `accessibility` · `data` · `resilience` · `observability` · `fundi` · `safety` | mzizi |
| Shipped (Nyuchi-authored, part of Mzizi) | `brand` · `pages` · `shell` | nyuchi |
| Swappable | `styling` · `components`/framework · `icon library` | bundu / framework |
| Spine | `harness` (the pre-wiring backbone) | nyuchi |
| Genetic code | `ubuntu` · `conventions` (the readable sequence under the helix) | bundu |
| Documentation / transcription | `documentation*` collections | bundu |

The locked model lives in `changelog/4.1.0`. The full per-node detail is in `documentation-architecture-nodes/*`. The classification (`dnaRole`) is stamped on every document in the store.

## Data architecture — substrate and lifecycle

The data architecture describes how the platform stores, owns, and moves data. It does NOT inherit the DNA helix vocabulary. Its concerns are different: durability, sovereignty, sync, lifecycle, and ethical lifecycle (PII strip, anonymisation, commons publication).

### The four-category ownership model (the spine of the data architecture)

| Category | Database | Lifecycle |
| -- | -- | -- |
| `personal` | Postgres (FK roots) + Mongo (operational content) | pre-verification, platform-readable |
| `personal-sovereign` | Honeycomb Pod | post-verification, user-private |
| `community` | MongoDB (operational primary) | community-shared |
| `platform-open` | Apache Doris (via Flink privacy filter) | public-open |

`personal` → `personal-sovereign` is one category at two lifecycle points. Data starts platform-readable and migrates to the sovereign Honeycomb Pod at identity verification (tier 2+).

### The substrate (current decision, per `genetic-code-conventions/substrate-decision`)

| Role | Technology | Notes |
| -- | -- | -- |
| Operational primary (non-relational) | **MongoDB** | medium-risk sovereignty assessment; tiered, not disqualified |
| Operational primary (relational) | **PostgreSQL** (via Supabase for Mzizi DB; self-managed for product data) | low-risk |
| Connective fabric / service mesh / event bus | **NATS** | edge-native |
| Event streaming → analytics | **Redpanda** | Kafka-compatible, feeds Flink |
| Analytical engine + open data commons | **Apache Doris** | the Nhaka tier |
| Privacy filter / stream processing | **Apache Flink** | PII strip before Doris |
| Sync protocol | **SiafuDB Graph Sync** (canonical); RxDB replication (interim until SiafuDB ships) | first-party Bundu project |
| Device layer | **RxDB · SQLite · IndexedDB / Dexie · PouchDB** (legacy) | local-first foundation |
| Future cold-storage tier | **ScyllaDB** | re-roled for Nhaka cold tier; not currently active |
| **Removed from the stack** | Apache CouchDB, Cloudflare D1 | see `documentation-architecture-removed/*` |

### Data architecture principles

| Principle | What it requires |
| -- | -- |
| **Local-first** | Apps function fully offline on the device layer; sync is bidirectional and conflict-resolving |
| **Mobile-first** | The device layer is the design surface, not the cloud |
| **Open data** | The Nhaka tier (Doris) is public; data published under CC BY 4.0 |
| **Open source & sovereign** | Every substrate technology has a written sovereignty assessment |
| **Sovereignty assessment** | The rule: no technology enters the stack without a written assessment (see `documentation-architecture-principles/sovereignty-assessment`) |
| **Ubuntu** | Tri-mode is mandatory at every layer (Musha / Basa / Nhaka — see `genetic-code-conventions/tri-mode`) |

## The seam — where the two architectures meet

The application architecture and the data architecture intersect at exactly one defined point: the **`data` node** in the Mzizi core (one of the seven core guarantee nodes). The `data` node is the application-side interface to the data architecture. From the application's point of view, the data node provides:

- a uniform read interface (resolves to the right substrate by category)
- a uniform write interface (routes to the right store by ownership category)
- the local-first cache (RxDB / SQLite on device)
- the sync protocol (SiafuDB Graph Sync)

From the data architecture's point of view, the `data` node is the consumer. The data architecture does NOT care what UI sits above it — only that callers respect the four-category lifecycle and the substrate's storage semantics.

This seam is why the two architectures must stay distinct: they evolve on different timescales (UI faster, data slower), are governed by different sovereignty concerns (which framework is acceptable vs. which database licence is acceptable), and serve different audiences (adopters care about the swap layer; the Foundation cares about the substrate).

## What this overview is NOT

- It is not the **product** architecture. Mukoko, Nyuchi Console, Shamwari AI each have their own product architecture, built on top of these two foundations.
- It is not the **infrastructure topology** (which Vercel projects, which Cloudflare Workers, which Supabase projects) — that is `documentation/infrastructure-topology` (forthcoming) and `infrastructure-topology` machinery rows.
- It is not the **commercial architecture** (Observability-as-a-Service tiers, pricing model) — that is `documentation/observability-as-a-service`.
