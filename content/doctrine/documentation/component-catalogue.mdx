# The Component Catalogue — How to Read a Component

Mzizi contains hundreds of components. This page explains how to navigate them, what each piece of metadata means, and how to find the right component for the right job.

Live counts: read `meta.registryTotal` on `GET https://api.mzizi.dev/v1/ui`, or the per-node counts on `GET https://api.mzizi.dev/v1/stats`, rather than relying on numbers in this page. The catalogue grows; this page does not need to.

## How a component is described

Every component is an item in `registry.json`, beside its files under `components/registry/n<N>-<node>/`. There is no database behind it. The item answers five questions a developer asks:

1. **What is this for?** — `title` and `description`
2. **Where does it live in the architecture?** — the `n<N>-<node>` directory its files are in; `meta.collection` and `categories` group it further
3. **Who owns it?** — `meta.owner`: `mzizi`, `nyuchi` or `framework`
4. **How do I install it?** — `dependencies`, `registryDependencies`, `files`
5. **How do I use it well?** — `docs`, and `meta.useCases`, `meta.variants`, `meta.sizes`, `meta.features` and `meta.a11y`; where it has one, `meta.contract` names its contract under `contracts/`

## Builds

A component's builds are sibling files in its directory: `.astro` (the default), `.rs` (Mzizi Roots, Dioxus, shipped in a node crate on crates.io) and `.tsx` (React). Each is the same component, held to the one contract. Not every component has every build yet: `GET https://api.mzizi.dev/v1/astro` lists the Astro ones, and `mzizi_get_component` returns every build of one component. The N1 tokens also ship per-platform files (Swift, Kotlin, ArkTS, React Native, Python, Rust).

## Change and renames

The registry carries no per-component status field: an item in `registry.json` is published. Breaking changes, deprecations and removals are announced in `CHANGELOG.md`, and a renamed component's former name keeps resolving to its successor (`lib/component-renames.json`).

## Architecture node

Every component belongs to exactly one node. See `/architecture/architecture-overview` for the full node definitions. The node determines what the component can do, what it must not do, and what it can depend on.

The rule of thumb:

- **N2 Primitives** — leaf components, no harness, no brand styling
- **N3 Brand** — primitives with Ubuntu in them; the visible aesthetic
- **N6 Pages** — composition only; no inline buttons or cards
- **N7 Shell** — the application skeleton

If a component crosses a node boundary, it is wrong. The N4 Safety, N5 Resilience, and N8 Assurance nodes are special — they wrap components rather than render them.

## How to find the right component

Four ways:

1. **By node** — `GET https://api.mzizi.dev/v1/search?node=3`, or `mzizi_list_components` with `node`
2. **By keyword** — `GET https://api.mzizi.dev/v1/search?q=form`, or `mzizi_search`
3. **By category** — `GET https://api.mzizi.dev/v1/search?category=<category>`
4. **By browsing** — the visual catalogue at `mzizi.dev`

Whichever you use, `registry.json` and the files on disk are the source of truth.

## Versioning

The registry records a component change in `CHANGELOG.md`, in the pull request that makes it; see `documentation/changelog-system`. A component's version history is machine-written data that belongs to the Mzizi console, so `GET /v1/ui/{name}/versions` answers `503` and names the console.

## When to write your own

Don't. Almost always, the answer is a primitive or brand component already exists. If you cannot find one, search by category, ask the MCP, or check the node-decision-guide. Only after exhausting those options should you scaffold a new one.

When you do scaffold a new component, follow `/contributor/contributing` and read the relevant node's `implementation_rules` from `documentation-architecture-nodes` first.
