# The Component Catalogue — How to Read a Component

The Nyuchi Design System contains hundreds of components. This page explains how to navigate them, what each piece of metadata means, and how to find the right component for the right job.

Live counts: query `SELECT * FROM get_system_counts();` rather than relying on numbers in this page. The catalogue grows; this page does not need to.

## How a component is described

Every component has a row in `public.components` and a paired row in `public.component_docs`. The first row holds identity and metadata; the second holds usage documentation. Together they answer five questions a developer asks:

1. **What is this for?** — `description` field in `components`
2. **Where does it live in the architecture?** — `ecosystem_node` (1–10) and `node_label` sub-label
3. **Is it ready to use?** — `status` (alpha / beta / stable / deprecated)
4. **How do I install it?** — `dependencies`, `registry_dependencies`, `files`
5. **How do I use it well?** — `use_cases`, `variants`, `sizes`, `features`, `a11y`, `examples` from `component_docs`

## Component lifecycle

The `status` field tracks where a component is in its journey:

| Status | Meaning | Stability promise |
|---|---|---|
| `alpha` | Recently added, experimental | API may change without notice |
| `beta` | Stabilising, real-world testing | Breaking changes only with warning |
| `stable` | Production-ready | API is locked; only additive changes |
| `deprecated` | Replaced by something better | Will be removed in a future major version |

## Architecture node

Every component belongs to exactly one of the ten nodes. See `/architecture/architecture-overview` for the full node definitions. The node determines what the component can do, what it must not do, and what it can depend on.

The rule of thumb:

- **N2 Primitives** — leaf components, no harness, no brand styling
- **N3 Brand** — primitives with Ubuntu in them; the visible aesthetic
- **N6 Pages** — composition only; no inline buttons or cards
- **N7 Shell** — the application skeleton

If a component crosses a node boundary, it is wrong. The N4 Safety, N5 Resilience, and N8 Assurance nodes are special — they wrap components rather than render them.

## Mini-app association

The `mini_apps` array on each component lists which of the Mukoko mini-apps primarily use it. A component used by every mini-app sits at N2 or N3; a component used by only one (e.g. `bushtrade-listing-card`) sits at N6.

## Platforms

The `platforms` array names the runtimes a component targets. Web is the default. Some components also support `ios`, `android`, `harmonyos`, `react-native`, `rust`, `python`, `postgres`, or `edge-function`. Cross-platform components are rare and intentional.

## How to find the right component

Four ways:

1. **By node** — `SELECT name FROM components WHERE ecosystem_node = 3 ORDER BY name;`
2. **By keyword** — `SELECT name FROM components WHERE name ILIKE '%form%' OR '%form%' = ANY(tags);`
3. **By mini-app** — `SELECT name FROM components WHERE 'bushtrade' = ANY(mini_apps);`
4. **By MCP tool** — call `list_components` to filter by node, status, platform, or mini-app, or `get_node_documents` to pull a whole collection.

The portal at `mzizi.dev` provides a visual catalogue with filters, but the database is always the source of truth.

## Versioning

Every change to a component writes a row to `public.component_versions`. The `change_type` enum tells you what kind of change it was: `created`, `source_updated`, `metadata_updated`, `status_changed`, `node_moved`, `dependencies_changed`, `promoted`, `deprecated`, `breaking_change`, `bugfix`, `enhancement`, `refactor`, `tokens_wired`, `enterprise_upgrade`. Reading the version history of a component tells you the story of how it grew up.

## When to write your own

Don't. Almost always, the answer is a primitive or brand component already exists. If you cannot find one, search by tag, ask the MCP, or check the node-decision-guide. Only after exhausting those options should you scaffold a new one.

When you do scaffold a new component, follow `/contributor/contributing` and read the relevant node's `implementation_rules` from `documentation-architecture-nodes` first.
