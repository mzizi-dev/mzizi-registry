# Nyuchi Brand Guidelines

## Philosophy

Ubuntu — "I am because we are." Our design language reflects African heritage, community-first values, and technological ambition.

## The Seven African Minerals

Our colour palette is seven minerals dug from African earth. Each carries a one-word ROLE — the role is a functional contract, not a mood — and the seven split into two families: the deep earth (cool, luminous, the future the continent builds) and the hand (warm, grounded, what the continent has always worked). For canonical hex values, container colours, role, and family, query the `styling-minerals` collection — the database is the source of truth. This page describes what each colour _means_; the database describes what each colour _is_. Full doctrine: `genetic-code-conventions/seven-minerals`.

### Deep-earth family

#### Cobalt — Knowledge

Source: Katanga Copperbelt, DRC & Zambia. Links, calls-to-action, anything that teaches or opens a door. The blue of the digital future, grounded in the mineral wealth of the Copperbelt.

#### Sodalite — Intelligence

Source: Kunene River, Namibia & South Africa. AI and Shamwari surfaces, reasoning, deep-thinking states. The blue of a sovereign machine mind.

#### Tanzanite — Identity

Source: Merelani Hills, Tanzania (the only place on Earth where tanzanite is found). The Mukoko signature — super-app shell, social surfaces, who-you-are. Rare, precious, uniquely African.

#### Malachite — Growth

Source: Congo Copper Belt. Success states, health, positive change — the green light to go.

### Hand family

#### Gold — Value

Source: Ghana, South Africa, Mali, Zimbabwe. Commerce, payments, achievements — the moment value changes hands. The material of honour across African cultures.

#### Copper — Stewardship

Source: Central African Copperbelt, Zambia & DRC. Bundu, the commons, the foundation everything stands on. The metal drawn into connection.

#### Terracotta — Community

Source: Pan-African Sahel. Ubuntu, belonging, anywhere people gather. The clay of home — grounding, tactile, shared.

## Design Tokens

All visual design values live in dedicated database tables under the `brand_*` prefix. Each table is the canonical source for its category. Run `SELECT * FROM get_token_counts()` to see the live row counts for every brand\_\* table.

### Visual tokens

- `styling-minerals` — the seven palette colours with light/dark/container/on-container values, plus role and family
- `styling-semantic-colors` — semantic role mappings (foreground, background, border, ring, primary, accent, error, success, warning, info, and container variants), plus `hc_light_value` and `hc_dark_value` for high-contrast mode
- `styling-spacing` — the spacing scale from 2px hairline to 128px page-hero
- `styling-typography` — font families and type scale, with `letter_spacing`, `fluid_min_px`, `fluid_max_px`, and `font_features` columns for modern responsive typography
- `styling-radius` — border-radius scale including the pill radius used for buttons, inputs, avatars, badges, and toggles
- `styling-shadow` — compound shadows with light and dark variants
- `styling-motion` — durations, easings, and stagger timings with reduced-motion fallbacks
- `styling-breakpoints` — responsive breakpoints with max-content-width ceilings
- `styling-z-index` — banded stacking scale across six categories

### Sizing & accessibility tokens

- `styling-icon-sizes` — canonical icon dimensions from xs (12px) through xl (40px), default 20px
- `styling-touch-targets` — accessibility tier minimums (superseded for the minimum by the Bundu floor below: 49px on touch, 28px on a desktop) with WCAG, Apple HIG, and Material Design citations per row
- `styling-component-specs` — per-component canonical heights, padding, variants, border-radius, and minimum touch targets for primitives like button, input, avatar, badge, card, dialog, toggle, checkbox, tabs

### Density tokens

- `styling-density` — three tiers (compact for desktop dashboards, comfortable as the Nyuchi default for mobile/tablet, spacious for hero and landing surfaces). Each tier references other token tables by name (spacing_component, touch_target, icon_size, body_type, heading_type, radius_card) rather than hardcoding numeric values
- `styling-density-breakpoints` — viewport-to-default-density mapping that determines which tier loads at which screen size

### Accessibility validation

- `styling-accessibility-checks` — WCAG contrast ratios and color-blindness safety flags for every critical semantic-color pair, in both light and dark modes. Each row carries the contrast ratio, WCAG AA/AAA compliance booleans, and protanopia/deuteranopia/tritanopia/achromatopsia safety flags

Three SQL functions support contrast validation directly in the database:

- `hex_to_rgb(hex)` — hex → (r, g, b) tuple
- `relative_luminance(hex)` — WCAG relative luminance for a hex color
- `calculate_contrast_ratio(fg_hex, bg_hex)` — WCAG 2.1 contrast ratio between two hex colors. WCAG AA requires 4.5 for normal text (3.0 for large), AAA requires 7.0 (4.5 for large)

A summary report is available via `SELECT * FROM get_accessibility_summary()`.

This page deliberately does not duplicate the values from these tables, because two sources of truth inevitably drift. To see current token values, query the relevant table or use `get_token_counts()` for a summary.

## Typography

Three font families, chosen for complete coverage of African scripts including Latin, Arabic, Ethiopic, Tifinagh, and Bamum:

- **Noto Serif** — page titles, hero text, display headings. Editorial feel with full language coverage.
- **Noto Sans** — body text, UI labels. Neutral, highly legible, same coverage as Noto Serif.
- **JetBrains Mono** — code blocks, terminal output, technical content. Purpose-built for developer readability.

The type scale runs from Display (40px serif on a phone, 48px on tablet and desktop) through Display Small, H1-H6 (34-17px on a phone, 32-17px on desktop, mixing serif and sans), Body Large/Body/Body Small (18px, 17px, 14px on touch; 17px, 15px, 14px on a desktop), Caption (14px sans), and Code (14px mono). Body text is 17px on touch and 15px on a desktop, and nothing readable is under 14px on any device: that is the Bundu floor, below. Display sizes carry `fluid_min_px`/`fluid_max_px` so they scale responsively rather than breaking to one word per line on phones. Display through H4 carry negative letter-spacing for typographic refinement; Caption carries small positive tracking; Code carries `tabular-nums` so numbers align in tables.

Lowercase wordmarks (mukoko, nyuchi, shamwari, bundu) are reserved for special instances — the brand wordmark lockup itself: logos, splash marks, and standalone brand marks. In site names, product names, and running text, Bundu and Nyuchi take capitals: Bundu Docs, Nyuchi Docs, Nyuchi Platform. Mukoko is the exception — it only uses lowercase, in every context. This is a brand decision, not a typography accident.

## Contrast Minimums

The contrast standard is APCA 3.0 AAA with explicit WCAG 2 minimums beside it (owner decision, 2026-11-02, mzizi-registry#399). Both are enforced: `pnpm tokens:sync` and `pnpm tokens:verify` fail when a default role is under its minimum. The three numbers are the named exports `WCAG_BODY`, `WCAG_NON_BODY` and `WCAG_UI` in `lib/tokens/roles.source.ts`, beside the APCA bars `BODY`, `NON_BODY` and `UI`.

| Part                                                                 | APCA  | WCAG 2 minimum |
| -------------------------------------------------------------------- | ----- | -------------- |
| Body text, on `base` and `surface`, both themes                      | Lc 75 | 7:1            |
| Non-body text: captions, timestamps, metadata                        | Lc 60 | 4.5:1          |
| UI parts that must be seen: focus rings, control edges (WCAG 1.4.11) | Lc 30 | 3:1            |

The label on a brand's solid action fill (`primary-foreground` and the roles that follow `primary`) is held to 4.5:1 rather than 7:1, and so is `destructive-foreground` on the destructive fill (canon error `#B3261E`, 6.54:1; pending owner confirmation, 2026-11-02). It is a button label, not body copy, and the fill is each brand's `-aa` tier; 7:1 would darken every brand's action colour. The gate prints that exception and the role tests pin it.

## Touch Targets

Owner ruling, 2026-11-02: every interactive control keeps a **49px hit region on touch**. Owner ruling, 2026-11-12 (#660: "yes do the device-based floor, desktop body 15px"): the floor has two pointer tiers, and a desktop (a fine pointer with hover) keeps a **28px hit region and 15px body** (Apple's macOS defaults are a 28 pt control and 13 pt body), captions still 14px. The 49px hit region replaces the 44px floor on a coarse pointer (Apple's Buttons page: "a button needs a hit region of at least 44x44 pt", read 2026-11-01 at developer.apple.com/design/human-interface-guidelines) on touch; the desktop tier stays above the 24px floor of WCAG 2.2 SC 2.5.8. Bundu sets the standard for outdoor reading and for people who find technology hard (older users, African and emerging markets), so the minimum is as high as it can be and one Bundu will stand by.

- **Coarse pointer (phones, tablets):** controls are drawn at 49px (the large control 56px), body text is 17px, the hit region is 49px. The gaps between targets stay generous: spacing tokens are untouched.
- **Desktop density (fine pointer, hover, 64rem and up):** controls are DRAWN 28-40px (`--control-floor`, 28px) and the hit region is 28px (`--target-floor`, lowered by the desktop layer only), so a desktop control's drawn box is its hit region. A native field or select is drawn 32-36px. Body text is 15px, captions stay 14px.
- Density is about visual size only. It is never a guess about the network: laptops and iPads are usually on wifi, and the performance budgets do not change with it.

The sizes consumers pinned before 2026-11-01 (48px and 56px targets, 16px body, 12px captions) come back with `data-mzizi-sizes="legacy"` on the root element, until the app has migrated; that attribute steps out of the Bundu floor, so remove it to take it. The older tiers in `styling-touch-targets` (48 accessible, 56 comfortable) are superseded by this section.

## Spacing Floor

Owner ruling, 2026-11-04 (mzizi-registry#617): the Bundu floor also sets **minimums for space**, that nothing can go under, even a component that sets no padding at all. They are the named values `BUNDU_FLOOR.spacing` in `lib/tokens/roles.source.ts`, on the 7px unit, and `/v1/brand` carries them in `brand_meta.accessibility`.

| Floor                    | Value | CSS custom property | Meaning                                                                                                                                                 |
| ------------------------ | ----- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Inset (`insetPx`)        | 14px  | `--inset-floor`     | Padding between text and the edge of its container (2 x 7). A control's label on the inline axis; a card, panel, dialog, alert or popover on both axes. |
| Control gap              | 7px   | `--gap-floor`       | Gap between adjacent interactive controls, visible edge to visible edge. Hit regions may touch, never overlap.                                          |
| Label gap (`labelGapPx`) | 7px   | `--gap-floor`       | Gap between a label and its field.                                                                                                                      |
| Item gap (`itemGapPx`)   | 7px   | `--gap-floor`       | Gap between sibling items of a list, grid, stack or toolbar.                                                                                            |
| Body leading             | 1.5   | `--leading-floor`   | Body line height, never tighter (WCAG 1.4.12). Headings and display type keep their own tighter leading.                                                |

- **Enforced as defaults and as tests.** The base layer of `mzizi-tokens-globals.css` gives a bare control (a `button`, `select`, `textarea`, a text `input`) `padding-inline: var(--inset-floor)`, a bare text surface (a native `dialog`, a `[popover]`, an alert, a tooltip, a card with no structured children) `padding: var(--inset-floor)`, a list, group, toolbar or tablist `gap: var(--gap-floor)`, and `body` `line-height: max(var(--lh-body), var(--leading-floor))`. A utility on the element (`p-6`, `gap-2`) is the author's own value and wins, so the tests hold every explicit value to the floor.
- **A control's block axis is held by its height.** 14px of block padding does not fit a control drawn at 28px, so a control's vertical room is decided by the 28px drawn and hit-region floors (49px on touch), not by the inset.
- **Hit regions may touch, never overlap.** The gap floor is measured between visible edges; the `hit-area` overlay of the hit-region floor may reach into neighbouring space as before.
- **No `p-0`, `gap-0` or negative margin on a text container** without an explicit exception: a `spacing-floor: exception <reason>` comment in a component, or a pinned entry with a reason in the contract runner (today a chart's 1px bars, a joined search-and-submit toolbar, an image that bleeds to a card edge, and inline code).
- **No brand pack, density layer or component may lower a floor.** `data-mzizi-sizes="legacy"` steps out of it with the other Bundu floors.

`__tests__/spacing-floor.test.ts` fails when the floor numbers differ between `BUNDU_FLOOR`, canon, `/v1/tokens` and the stylesheet, when a density layer lowers a variable, or when the base-layer rules are gone.

## The Bundu Order

The Bundu Order draws on biblical mathematical patterns and prime numbers (owner, 2026-11-02). This section states only what the code holds, in `lib/tokens/roles.source.ts` (`BUNDU_FLOOR`), `lib/tokens/brand.source.ts` and `scripts/render-globals-css.ts`.

- **The unit is 7px** (`--radius-unit`). The radii are 4, 7, 12, 14 and 17px and a pill, and they do not change.
- **P7 and P17** are prime steps of the surface-elevation ladder (`surface` is P7, `raised` is P17), and the seven experimental families are a heptagon of hues offset 17 degrees.
- **The floors derive from the same numbers.** Body text is 17px on touch (a prime; Apple's iOS default body size) and 15px on a desktop (owner, 2026-11-12). Captions, metadata and secondary labels are 14px (2 x 7), and nothing readable is smaller. Every interactive control keeps a 49px hit region on touch (7 x 7, above Apple's 44 pt) and a 28px one on a desktop (4 x 7, Apple's macOS default control).
- **Spacing** floors stand beside them: 14px of inset (2 x 7), 7px gaps (the unit) and 1.5 body leading (see Spacing Floor).
- **Contrast** floors stand beside them: body text 7:1, non-body text 4.5:1, UI parts 3:1 (see Contrast Minimums).

`__tests__/bundu-floor.test.ts` fails when a default type step, a size role or a desktop control breaks any of these.

## Density

Three tiers in `styling-density`:

- **Compact** — desktop dashboards, admin tables, power-user tools
- **Comfortable** (Nyuchi default) — phones, tablets, general consumer surfaces
- **Spacious** — landing pages, marketing surfaces, onboarding, long-form reading

Each tier composes other tokens by reference rather than duplicating values. The `styling-density-breakpoints` table maps viewport sizes to default density tiers so the right tier loads automatically.

## Motion

All motion respects `prefers-reduced-motion`. Every row in `styling-motion` carries a `reduced_motion_fallback` value that components must honour when the user has requested reduced motion. Four duration tiers (quick 100ms, standard 200ms, emphasis 350ms, dramatic 500ms) and four easing curves (entrance, exit, standard, spring) cover the full motion language.

## High-Contrast Mode

`styling-semantic-colors` carries `hc_light_value` and `hc_dark_value` columns alongside the standard `light_value` and `dark_value`. When high-contrast mode is active, the design system reads from the HC columns. NULL means "fall back to the standard value." Every populated HC value has been verified to meet WCAG AAA (7:1 contrast) against typical backgrounds.

## Color-Blindness Safety

Every critical foreground-on-background pair is tracked in `styling-accessibility-checks`. Pairs with luminance contrast ≥ 7:1 are universally safe because they rely on lightness, not hue, to remain distinguishable. Pairs that depend on hue discrimination — particularly red/green semantic states (error vs success) — must be paired with an icon or label so colour is not the sole channel conveying meaning.

## RTL Support

Components must use logical CSS properties (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `border-inline-end`) instead of physical (`margin-left`, `padding-right`, `left`, `border-right`). Text alignment uses `start`/`end`, not `left`/`right`. Directional icons (arrows, chevrons, undo/redo) should be marked `data-rtl-mirror="true"` so they flip in RTL contexts. The `rtl-conformity-check` N8 component validates these rules at runtime and reports violations.

## Component Specs

Certain components carry brand-identity decisions that are non-negotiable. These live in `styling-component-specs` and include the pill-shaping rule: buttons, inputs, avatars, badges, and toggles always use borderRadius 9999. Query that table before creating new components that resemble these categories, so the brand identity is preserved.

## Accessibility Healing Loop

The system runs a daily accessibility audit that validates every non-exempt pair in `styling-accessibility-checks` under four color-blindness simulations. When a regression is detected, it files a Fundi issue through the normal N8→N9 healing loop. This means the palette is continuously validated rather than checked once at release time.

The audit is registered as the N8 component `accessibility-audit` and runs via pg_cron job `nyuchi-accessibility-audit-daily` at 02:00 UTC.

To run the audit on-demand:

```sql
SELECT * FROM run_accessibility_audit(p_file_fundi_issues := true);
```

To preview how a specific colour appears under a specific condition:

```sql
SELECT simulate_color_blindness('#0047AB', 'deuteranopia');
```

Decorative pairs can be exempted by setting `audit_exempt = TRUE` with a reason, following the WCAG 1.4.11 (Non-Text Contrast) exemption for borders that do not convey state or meaning.
